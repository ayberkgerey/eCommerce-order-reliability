# 1. BUSINESS PROBLEM

Imagine an e-commerce company processing thousands of orders during high-traffic events such as Black Friday.

Its existing architecture has several problems:

- Order processing is tightly coupled with notification and warehouse operations.
- A temporary failure in one service can interrupt the entire order workflow.
- Traffic spikes can overwhelm downstream services.
- Failed orders are difficult to track.
- Retrying failed operations can create duplicate processing.
- The company has insufficient visibility into processing failures.

The business needs a more reliable architecture.

The goal is to redesign the order processing workflow using AWS managed services.

The new architecture must:

- Decouple order processing from downstream services.
- Buffer incoming orders during traffic spikes.
- Process orders asynchronously.
- Handle temporary processing failures.
- Isolate permanently failed messages.
- Provide operational visibility through CloudWatch.

# 2. PROPOSED AWS ARCHITECTURE

Use the following AWS services:

- Amazon SQS Standard Queue
- Amazon SQS Dead Letter Queue (DLQ)
- AWS Lambda
- Amazon SNS
- Amazon CloudWatch
- AWS IAM

Architecture workflow:

1. An order producer sends JSON order messages to Amazon SQS.
2. SQS stores incoming messages independently of the processing system.
3. Lambda is triggered through an SQS event source mapping.
4. Lambda processes incoming orders.
5. Successful orders trigger an SNS notification.
6. Failed orders are retried according to the SQS redrive policy.
7. Messages exceeding the maximum receive count are moved to the Dead Letter Queue.
8. CloudWatch collects Lambda logs and operational metrics.

Use a standard SQS queue, not FIFO, to demonstrate distributed asynchronous processing.

Do not claim exactly-once processing. Explain SQS Standard's at-least-once delivery semantics and the possibility of duplicate processing. Document idempotency as an important production consideration.

- aws_iam_role_policy for required permissions.
- aws_sns_topic for order notifications.
- Optional SNS email subscription controlled by a Terraform variable.
- aws_cloudwatch_log_group for Lambda logs.

Use appropriate resource dependencies.

Use a configurable AWS region with eu-central-1 as the default.

Set sensible defaults for Lambda memory and timeout.

Set SQS visibility timeout to at least six times the Lambda timeout.

Configure Lambda partial batch failure reporting using ReportBatchItemFailures so successful messages do not need to be retried when another message in the same batch fails.

Configure a reasonable batch size.

Use a maximum receive count of 3 for the DLQ redrive policy.

# 4. LAMBDA FUNCTION

Use Node.js 22 and AWS SDK for JavaScript v3.

Create exactly one Lambda function.

Responsibilities:

- Receive SQS event batches.
- Parse JSON order messages.
- Validate required order fields.
- Process each order independently.
- Log order IDs and processing results.
- Publish successful order notifications to SNS.
- Return failed message identifiers using partial batch failure responses.
